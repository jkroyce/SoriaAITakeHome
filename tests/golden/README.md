# tests/golden — the falsifier

Agents on this project write rules for themselves into `skills/*.md`, and those rules
are injected into later prompts. That is the self-improvement layer, and it is the part
most likely to degrade without anyone noticing: a prompt is not a diff you can read for
correctness. This directory is the fixed measuring stick that makes
"the agent improved" a claim you can be wrong about.

From `docs/plans/03-end-to-end-architecture.md`:

> A candidate rule is accepted only if it does not regress the **golden set**
> (`tests/golden/` … the seven-company pool and the $180M modification).
> **Without this, "self-improvement" is unfalsifiable.**

The acceptance test for this directory is therefore not "how many fixtures are in it"
but: **a deliberately bad rule must be caught and rejected.** That is
`tests/test_golden.py::test_a_deliberately_bad_rule_is_rejected`.

## Run it

```bash
# score the extractor against the golden set, replaying the committed cache.
# Never calls the API: a cache miss is reported BLOCKED, not paid for.
.venv/Scripts/python.exe tests/golden/runner.py

# what is in the set
.venv/Scripts/python.exe tests/golden/runner.py list

# everything, as pytest (fixture integrity + runner behaviour + the bad-rule gate)
.venv/Scripts/python.exe -m pytest tests/test_golden.py -q
```

Exit codes, so a promotion step can just test the status:

| code | meaning |
|---|---|
| 0 | every check passed |
| 1 | at least one check FAILED — a regression |
| 2 | no failures, but at least one case was BLOCKED and could not be scored |

**BLOCKED is not a pass.** With `cache/llm/` empty the whole set is blocked and the gate
refuses promotion, because it cannot show a rule did no harm.

## What is in here

```
cases/            the fixtures: 9 cases, 53 checks, over 2 real announcements
prose/            committed snapshots of the announcement text + their sha256
runner.py         scores extraction output against the fixtures; also the gate
stubs/            hand-written stand-ins for model output, to test the runner offline
candidate_rules/  plausible-but-wrong rules, and one harmless control
```

### The fixtures are ground truth, not recorded behaviour

Every expected value was read out of the announcement prose by a human, and every
check carries the sentence it came from in a `quote` field plus a `reason` saying why
that reading is right. `test_every_quote_is_really_in_the_announcement` asserts each
quote is literally present in the source text, so the traceability is machine-checked
rather than promised.

Nothing here was produced by running the extractor and writing down its answer. A set
built that way agrees with any regression, because the regression is what defined it.

**Status, stated plainly: all 9 cases are verified against the source prose. None are
verified against real model output — `cache/llm/` is empty and this section spent
$0.00.** When the paid extraction pass warms the cache, `runner.py` scores real output
through exactly the same code path with no changes.

### The checks

A check selects rows and asserts something. Three kinds:

| kind | meaning |
|---|---|
| `row` | the selector must match exactly one row; every field in `expect` must equal it |
| `count` | the selector must match exactly `expect` rows |
| `absent` | the selector must match no rows |

Selectors are exact values, or `{"in": [...]}`, `{"contains": "..."}`,
`{"startswith": "..."}`, `{"not": v}`, `{"is_null": true}`. `True` is not `1` and
`False` is not `0` — a null bid count and a stated zero are different answers.

Failures print the check id, the selector, the field, the expected value, the actual
value, and the quote. A gate that prints "3 failed" is not a gate anyone will act on.

### Why stubs exist

`cache/llm/` is empty, so the extractor cannot run. The fixtures are pure data and cost
nothing, but a runner nobody has watched score anything is not a gate. `stubs/good/`
is a hand-entered "what the model should have said" payload; it flows through the real
`extract_document`, with the real repairs and the real deterministic provenance fill,
and only the response bytes are substituted. There is no second "real mode" to keep in
sync.

A stub is a test double for the *runner*. It is not evidence about the model and it is
not the golden expectation.

Each `stubs/bad_rule_*/` directory is generated by applying, mechanically, the
transformation its paired candidate rule prescribes:

```bash
.venv/Scripts/python.exe tests/golden/stubs/build_stubs.py
```

so the bad-rule test asks the right question — *if an extraction behaved the way this
plausible-sounding rule tells it to, does the golden set reject it?* — rather than
"does the set reject something chosen to fail". `test_bad_stubs_are_derived_from_the_good_one_not_hand_written`
re-derives them and compares.

## The promotion gate

`.claude/skills/golden-verify/SKILL.md` describes the procedure. `runner.py gate`
implements it:

```bash
# offline: the candidate's behaviour is supplied by its derived stub
.venv/Scripts/python.exe tests/golden/runner.py gate \
    tests/golden/candidate_rules/R-BAD-001-divide-pool-ceiling.md \
    --from stub tests/golden/stubs/good \
    --candidate-stub tests/golden/stubs/bad_rule_divide_pool

# with a warm cache: the candidate side re-extracts with the rule appended
.venv/Scripts/python.exe tests/golden/runner.py gate <rule.md>
```

The candidate rule is appended to a **temporary copy** of `skills/extraction.md` and
passed to `extract_document(skills_path=...)`. The real skills file is never written to:
this runner does not own it, and a gate that mutates the thing it is gating is not a
gate.

Verdicts: `REJECT` (fewer checks pass — exit 1), `UNPROVEN` (same pass rate; keep the
rule only if it covers a case the set does not, and say which), `PROMOTE` (more checks
pass), `REFUSE` (either side was blocked — exit 2).

On a warm cache the candidate side legitimately misses the cache, because appending a
rule changes the prompt and the cache is keyed on the prompt. That is not a bug in the
gate; it is the cost consequence CLAUDE.md warns about, showing up where it should:
promotion really does require paying for re-extraction, which is why it is batched and
priced first.

| `4586879-army-idiq-pool-seven` | 4586879 | 7 rows, `is_multi_award=true`, $160M shared ceiling on every row |
| `4586879-modification-p00002` | 4586879 | `modification`, $180M action, $280M cumulative — not a new award |
| `4586879-navfac-pool-ten` | 4586879 | 10-row pool worded differently; small-business differs per company |
| `4586879-small-business-asterisks` | 4586879 | 14 asterisked names kept byte-for-byte; the `*Small business` legend is not an award |
| `4586879-branch-headers` | 4586879 | header inheritance; `U.S. SPECIAL OPERATIONS COMMAND` → `OTHER` |
| `4586879-bid-counts` | 4586879 | "solicited" unstated stays null, never 0, never copied from received |
| `4586879-amount-vs-other-money` | 4586879 | cumulative / option-maximum / obligation are not `amount_usd` |

| `4585867-correction-is-not-an-award` | 4585867 | a `CORRECTION:` line emits no row; `DEFENSE ADVANCED RESEARCH PROJECTS AGENCY` → `OTHER` |

Two cases carry a `caveat` field naming the part of the expectation that is a
convention rather than a fact printed in the prose — the `option_exercise` label, and
the judgement that a correction notice is not an award. Read those before treating a
failure there as a defect.

## Adding a case

1. Read the announcement text in `prose/`, or `raw/articles/<id>.html`.
2. Write the expectation and paste the sentence it comes from into `quote`, plus a
   `reason`. If you cannot quote it, do not assert it.
3. `pytest tests/test_golden.py -q` — the integrity tests will tell you if the quote is
   not really in the source or the field is not in the frozen contract.
4. If the case covers a new announcement, add its prose snapshot and its digest to
   `prose/SHA256SUMS.json`, and its rows to `stubs/good/` so the runner's own tests
   still exercise the case offline.
